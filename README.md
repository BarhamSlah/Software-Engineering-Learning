# Software Engineering Learning

A practical, beginner-friendly course for learning **how to think and work like a software engineer**. This repository teaches general Software Engineering—not a Java, API, Git, or GitHub course.

## My learning starting point

- Current level: beginner with partial foundations, based on the initial assessment.
- Existing knowledge: some programming/OOP, Java, Git/GitHub, introductory PostgreSQL, and a banking console project.
- Main goal: understand how software engineers identify problems, analyze needs, design solutions, make trade-offs, test quality, deliver software, and maintain it.
- Language: clear B1–B2 English, with correct technical terms explained simply.
- Teaching style: practical problem first, then the theory needed to understand and solve it.
- Practice: scenario analysis, diagrams, written decisions, reviews, and test planning. Do not assign coding challenges unless I explicitly ask.

## The course's main practical project

We will develop one imaginary **Campus Service Request System** throughout the course. Students can report problems (for example, a broken classroom projector), staff can manage requests, and users can track progress.

This project is a learning case study—not a requirement to build a Java application. We will use it to practice the complete Software Engineering process:

**Problem → Stakeholders → Requirements → Design → Architecture → Quality & Testing → Delivery → Security & Reliability → Maintenance**

Each phase produces a small engineering artifact, such as a problem statement, stakeholder map, requirements list, use case, diagram, design decision, test plan, release plan, or maintenance proposal.

We will also use short examples from banking, shopping, and familiar applications when they explain a concept better.

## How every topic will be taught

1. **Practical situation:** start with a realistic problem or decision.
2. **Concept:** explain the relevant idea in simple English.
3. **Reasoning:** show how an engineer analyzes the situation.
4. **Artifact:** create or review a practical output (diagram, requirement, decision, test, plan).
5. **Trade-off:** compare options and explain why one may be better.
6. **Reflection:** check understanding with short questions.

Progress is measured by whether you can explain and apply an idea—not by hours watched or pages read.

## Important boundary

Java, APIs, databases, Git, and GitHub may appear as examples or tools, but this repository's purpose is broader: **general Software Engineering knowledge and engineering judgment**.
